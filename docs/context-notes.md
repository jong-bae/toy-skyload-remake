# 컨텍스트 노트

의사결정과 그 근거를 시간순으로 기록한다. 새 세션은 이 문서부터 읽는다.

## 배경 사실

- 원작은 **SkyRoads** (Creative Dimensions / Bluemoon Interactive, 1993)다. 슈팅 게임이 아니라 우주 도로 레이싱/플랫포머다.
- `dosplay/`는 DOSBox 0.74 실행 환경이다. 게임 파일은 `dosplay/C HDD/`, 실행 파일은 `PWORM.EXE`(18KB)이고, `dosplay/run.bat`로 구동한다.
- `original_file/`은 1995년판 공식 배포본으로 보인다. 실행 파일은 `SKYROADS.EXE`(30KB)이며, `HELPMENU`, `INTRO`, `MUZAX`, `ROADS` 등 일부 파일 크기가 `dosplay/C HDD/`와 다르다.
- `original_file/`과 `dosplay/`는 `.gitignore`로 저장소에서 제외한다.
- `original_file/readme.txt`의 배포 조건은 다음과 같다. "freeware… as long as you don't reverse engineer, and/or modify this program or any of its accompanying files… distributed as a single unit."

## 의사결정

### D-01 (2026-10-16) 웹 기술 기반으로 구현
- 결정: TypeScript + Vite + Three.js로 만든다.
- 근거: 브라우저와 데스크톱(Tauri)에 같은 코드를 쓸 수 있다. 게임 규모에 비해 Unity·Godot는 과하다.

### D-02 (2026-10-16) 데스크톱 배포는 Tauri
- 결정: 2차 계획에서 Tauri v2로 Windows exe를 만들고 GitHub Actions(`tauri-action`)로 Release한다.
- 근거: Electron보다 결과물이 훨씬 작다. 처음엔 Windows만, 코드 서명 없이 시작한다. (SmartScreen 경고는 감수)

### D-03 (2026-10-16) 수치 확보는 블랙박스 측정만
- 결정: `SKYROADS.EXE`, `PWORM.EXE`는 디스어셈블, 디컴파일, 디버거 분석을 하지 않는다. REA 도구도 쓰지 않는다. 수치는 DOSBox 플레이 녹화를 프레임 단위로 측정해 얻는다.
- 근거: readme.txt가 리버스 엔지니어링을 명시적으로 금지한다. 사용자가 블랙박스 측정 방식을 선택했다.
- 결과: 1:1 정밀 재현이 아니라 "원작 느낌" 재현이 목표가 된다. 체감 비교로 튜닝한다.

### D-04 (2026-10-16) 원작 에셋 비포함, 원작 맵 지원은 보류
- 결정: 원작 파일은 저장소와 배포물에 넣지 않는다. 자체 맵과 에셋이 기본이다. 사용자 폴더의 원작 데이터를 읽는 기능은 M7에서 다시 판단한다.
- 근거: readme가 "single unit, intact" 배포만 허용하므로 일부 파일만 포함하거나 변환본을 배포할 수 없다. 데이터 파일 포맷은 커뮤니티 공개 문서로 알 수 있지만, 그 문서도 결국 누군가의 역분석 결과라 모호함이 남는다.
- 미결: M7 시점에 포함 여부를 정한다. 제외해도 게임 완성에는 지장이 없다.

### D-05 (2026-10-16) 시뮬레이션은 고정 시간 간격, 결정론적
- 결정: 게임 로직은 고정 스텝으로 돌고 렌더링과 분리한다.
- 근거: 기기 성능과 무관하게 같은 손맛을 보장하고, 입력 리플레이로 회귀 테스트를 할 수 있다.

### D-06 (2026-10-16) M0 툴체인 버전
- 결정: Vite 8, TypeScript 7, Vitest 5, three 0.186을 쓴다. `npm create vite` 대신 설정 파일을 직접 작성했다.
- 근거: 설치 시점의 최신 버전이다. TypeScript 7은 Go 기반 네이티브 컴파일러라서 `baseUrl`, `moduleResolution: node` 같은 옛 옵션은 쓰지 않고 `moduleResolution: bundler`로 설정했다.
- 참고: `npm run build`에서 "청크 500KB 초과" 경고가 나온다. three 라이브러리 크기 때문이며 M6 최적화 때 다시 본다.

### D-07 (2026-10-16) 측정 단위계와 방법
- 결정: 전진 거리는 K(= 초점거리 × 카메라 높이) 단위, 좌우·높이는 카메라 높이 h(또는 칸 = ⅔h) 단위로 기록한다. 리메이크도 같은 투영(지평선 y=32/200)을 써서 화면을 재현한다.
- 근거: 화면 좌표만으로 원작 화각을 알 수 없지만, 위 단위로 저장하면 화각과 무관하게 같은 화면이 나온다.
- 속도는 SPEED 게이지 판독(시간 해상도 높음)과 지면 경계 직선 맞춤(절대값 보정)을 함께 쓴다. 지면 높이에 있는 경계(블록 앞면 아랫선, 평평한 바닥 끝)만 써야 s = 1/(y−32)가 성립한다.
- 실패한 방법: 경계 쌍 차이 히스토그램은 픽셀 양자화 간격에 몰려 쓸 수 없었다. 측면 날개는 지면보다 높아서 공식이 맞지 않았다.

### D-08 (2026-10-16) 측정 자동화는 데스크톱 점유
- 결정: 키 입력은 DOSBox 창이 맨 앞일 때만 보낸다. 앞이 아니면 즉시 중단한다.
- 근거: 사용자가 PC를 쓰는 중에 다른 창으로 키가 들어가는 것을 막기 위함이다. 실제로 로드 17~29 촬영 중 중단됐다.
- 운영: 남은 측정은 사용자가 자리를 비울 때 몰아서 실행한다.

### D-09 (2026-10-17) 원작 투영은 유사 3D, 리메이크는 같은 공식을 쓴다
- 사실: 좌우는 y=32로 수렴하고 깊이는 y = 8 + K/d로 매핑된다. 표준 원근이라면 두 기준점이 같아야 하는데 다르다. D-07에서 쓴 s = 1/(y−32)는 틀린 가정이었고, 그 때문에 화면 아래쪽 궤적 속도가 어긋났다.
- 결정: 물리는 타일·칸·h 단위로 시뮬레이션한다. 렌더링은 원작 느낌을 살리려고 이 매핑을 셰이더(정점 변환)로 재현하는 "클래식 카메라"를 기본값으로 검토한다. 표준 원근 카메라는 현대식 옵션으로 둔다.
- 근거: 등속 궤적 직선성과 줄무늬 타일 간격이라는 독립된 두 근거가 같은 기준점(y≈8)을 가리킨다.

### D-10 (2026-10-17) 중력은 표로 쓴다
- 결정: 표시 중력값(100, 400, 500, 600, 900, 1700)별 중력 가속도를 측정표로 두고 보간한다.
- 근거: 직선 관계식은 잔차가 최대 1.2 h/s²로 크다. 원작 중력값 종류가 6개뿐이라 표로 충분하다.

### D-11 (2026-10-17) M2 코어 물리 설계
- 고정 스텝은 70Hz로 정했다. 원작 녹화(VGA 70Hz)와 주기가 같아 리플레이 비교가 쉽다.
- 좌표 단위는 전진 z = 타일, 좌우 x = 칸(도로 왼쪽 끝 0, 중앙 3.5), 높이 y = h(카메라 높이)다.
- 레벨은 칸마다 표면 높이(top)를 갖는 높이맵이다. 블록은 top이 높은 칸이고, 구멍은 null이다. 공중에 뜬 블록(아래가 비어 있는 블록)은 표현하지 못하는데, 원작에 있으면 M4에서 확장한다.
- 속도, 좌우 속도, 중력, 점프 초기 속도 모두 측정표 보간으로 처리한다. 좌우 근사식(0.60 + 0.125×단계)은 6단계에서 −10%라 버렸다. 점프 초기 속도도 중력 900만 4.47로 낮아서 표로 둔다.
- 공중 이동은 등가속 정확해(y += vy·dt − ½g·dt²)를 쓴다. 오일러 적분은 튕김 높이를 18% 깎았다.
- 가정값: 우주선 길이 0.5타일(미측정), 추락 실패 높이 −1.5h, 착지 속도 2.2h/s 이하이면 튕기지 않는다.
- 원작과 다르게 둔 것: 원작은 정지 상태에서 도로 가장자리로 미끄러져 떨어질 때 0.46h/s로 천천히 가라앉고 옆으로 1.0h/s 밀려간다. 지금은 일반 중력으로 떨어진다. M4에서 원작과 나란히 비교해 맞출지 정한다.
- 연료, 산소, 블록 효과, 터널, 클리어 판정은 계획대로 M4에서 구현한다.

### D-12 (2026-10-17) M3 렌더링
- 클래식 카메라를 기본으로 구현했다. 정점 셰이더에서 원작 공식(y = 8 + K/d, 좌우는 y = 32로 수렴)으로 바로 클립 좌표를 만든다. 표준 원근이 아니라 삼각형 내부가 휘므로 전진 방향 면은 타일당 8조각으로 나눈다. 그릴 수 있는 최대 거리는 10.5타일(노면이 한 점으로 모이는 거리)이다.
- 재질은 면 방향별 단색 음영(윗면 1.0, 옆면 0.8, 앞면 0.65)을 정점 색으로 굽고, 조명 없이 원작처럼 평면 색으로 그린다. 조명·현대식 카메라는 M6에서 다룬다.
- 우주선은 보이는 모델만 깊이를 0.15타일로 줄였다. 충돌용 길이 0.5타일을 그대로 쓰면 원작 투영에서 세로 기둥처럼 늘어나 보였다. 원작 우주선은 평면 스프라이트다.
- 블록 높이를 1h에서 0.3h로 바꿨다. 원작 로드 4 측면 블록 앞면이 접지 행 102에서 20px(= 0.29h)이었다. 1h는 카메라 높이와 같아 윗면이 안 보이는 벽처럼 그려졌다. 근거 없는 0.5h 기호('=')는 없앴다.
- 출발 위치(z = 0.5) 뒤로는 도로가 거의 없어 화면 아래가 비어 보인다. M5에서 계기판이 화면 아래(130행 이후)를 덮으므로 그때 다시 본다.
- 화면 확인은 헤드리스 Edge에 CDP로 키 입력을 보내 찍었다(스크래치 스크립트, 저장소에는 넣지 않음).

### D-13 (2026-10-17) M4 게임 규칙과 가정값
- 특수 블록 효과는 원작에서 측정하지 못해 가정값으로 구현했고 `src/core/config.ts`에 모았다. Supplies는 밟으면 연료·산소 가득(보급 효과는 원작에서 관찰). Boost는 4배 가속, Sticky는 4배 감속, Slippery는 조종 불가, Burning은 폭발이다.
- Sticky는 3단계 아래로는 끌어내리지 않는다. 4배 감속이면 가속키를 눌러도 순감속이라, 멈추면 영영 빠져나올 수 없었다.
- 효과는 우주선 중심 아래 칸이 실제로 딛고 있는 높이일 때만 적용한다. 공중에서는 효과가 없다.
- 연료는 주행 거리에 비례해 줄고(기본 370타일), 산소는 시간에 비례해 준다(기본 208초). 연료가 바닥났을 때 실패로 처리하는 것은 가정이다.
- 터널은 칸 속성이다. 안에서 점프할 수 없고(원작 1회 관찰), 지붕(0.5h, 가정)보다 높이 떠서 들어가면 막힌 칸으로 취급해 충돌한다.
- 클리어는 우주선 앞부분이 마지막 줄 끝에 닿는 순간이다(가정).
- 재시작 대기는 원작 실측값을 쓴다(폭발 3.4초, 추락 5.1초, 산소 3초). 마지막 1초 동안 화면이 어두워진다.
- 리플레이는 스텝별 입력 비트마스크를 같은 입력 구간으로 묶어 저장한다. 골든 리플레이(`tests/replays/test-01.json`)는 자동 조종 플레이 결과를 저장한 것으로, 물리를 의도적으로 바꾸면 `UPDATE_REPLAY=1 npm test`로 다시 만든다. 파일 쓰기 때문에 `@types/node`를 개발 의존성에 추가했다.
- 화면 확인은 골든 리플레이 입력을 헤드리스 Edge에 실시간 키 이벤트로 재생해 찍었다. 실시간 재생은 수 ms씩 어긋나 끝부분 고속 점프에서 실패했는데, 이는 입력 타이밍 문제이고 시뮬레이션 재생 테스트는 정확히 클리어한다.

### D-14 (2026-10-17) M5 콘텐츠
- 스테이지 10개는 원작 맵을 쓰지 않은 자체 디자인이다. 구간을 조합하는 생성 스크립트로 JSON을 만들었고, 저장소에는 결과 JSON만 넣었다(스크립트는 스크래치). 앞으로는 JSON을 직접 고친다.
- 모든 스테이지는 자동 조종으로 클리어되는지 테스트한다(`tests/stages.test.ts`). 자동 조종은 줄마다 안전한 칸을 계획해 차선을 바꾸고, 스테이지별 목표 속도를 테스트에 둔다. 목표 속도를 낮추면 실패하는 것(가속 레일 13단계, 첫 비행 9단계, 빙판길 11단계)도 확인해서 테스트가 난이도를 실제로 거른다는 것을 확인했다.
- 설계 규칙: 1칸 구멍은 중력 500에서 13단계, 600에서 15단계 이상이어야 넘는다. 차선 이동 구간은 두 칸이 모두 바닥인 줄을 3줄 이상 둔다. Sticky 뒤 6줄 이상, 터널 출구 뒤에는 구멍을 두지 않는다. 중력 900 스테이지에는 블록 오르기를 두지 않는다(0.3h 블록을 넘는 시간이 0.1초 남짓).
- 스테이지는 원작처럼 처음부터 모두 열려 있다. 클리어 기록만 localStorage에 남기고, 저장소를 못 쓰는 환경에서도 동작한다.
- 메뉴는 DOM 오버레이다. 키보드와 마우스 클릭을 모두 받는다.
- 계기판은 원작 배치(가운데 SPEED 링 33칸, 안쪽 O2·FUEL, 양옆 GRAV-O-METER·JUMP-O-MASTER)를 따르되 그림은 새로 그렸다. 320×200 캔버스에 그려 픽셀 그대로 확대하고 화면 아래 70행을 덮는다. JUMP-O-MASTER 표시 의미는 원작에서 확인하지 못해 지상 IDLE, 공중 JUMP, 터널 안 LOCK으로 정했다.
- 효과음은 음원 없이 Web Audio로 합성한다. 이벤트는 직전 프레임과 현재 상태를 비교해 뽑고, 재시작 직후 프레임은 비교하지 않는다(연료가 차서 보급으로 오인).

### D-15 (2026-10-17) M6 현대적 연출
- 화면 모드를 두 가지로 나눴다. 클래식은 원작 투영과 단색 음영을 그대로 두고, 현대식은 원근 카메라·조명·네온·블룸·파티클을 쓴다. 기본값은 현대식이다(목표가 "원작 느낌 + 요즘 스타일"). C 키와 타이틀 메뉴로 바꾸고 설정은 localStorage에 남긴다. 물리·규칙·계기판은 두 모드가 같다.
- 렌더링은 `View` 인터페이스(setLevel, render, resize)로 분리했다. `main.ts`는 시뮬레이션 상태를 보간한 `Frame`만 넘긴다.
- 현대식은 타일 1칸을 1.6h로 늘려 원작처럼 길쭉해 보이게 했다. 계기판이 화면 아래 35%를 덮으므로 카메라는 우주선을 화면 중간에 두도록 우주선 바로 앞을 바라본다. 처음에는 멀리 바라봐서 우주선이 계기판에 가렸다. 속도에 따라 화각을 58°에서 최대 약 70°까지 넓혀 속도감을 준다.
- 네온 외곽선은 EdgesGeometry로 만들고 색을 2.2배 HDR로 줘서 블룸이 확실히 걸리게 했다. 블룸은 절반 해상도로 돌린다.
- 엔진 분사 파티클은 처음에 카메라 바로 앞으로 흘러와 우주선을 덮었다. 크기·개수·밝기·수명을 줄여 짧은 꼬리로만 보이게 했다. 폭발 섬광도 화면 전체를 덮어서 세기를 줄였다.
- 배경음악은 음원 없이 직접 작곡한 칩튠 루프다. 25ms마다 0.12초 앞의 음을 예약해서 타이머 오차를 흡수한다. 효과음과 같은 AudioContext를 쓰고, 메뉴에서는 작게, 플레이 중에는 크게 튼다.
- 성능: 소프트웨어 렌더러(SwiftShader)에서는 현대식 33 FPS, 클래식 60 FPS였다. GPU를 쓰는 헤드리스 Edge(이 PC, 800×600)에서는 두 모드 모두 60 FPS였다. 중급 노트북·전체 화면 확인은 남았다.
- 번들은 602KB(gzip 152KB)이고 대부분 three.js다. 한 번 받는 단일 페이지 게임이라 쪼개도 첫 로딩 총량이 같아서 경고 기준만 700KB로 올렸다.

## 미결 사항

- 21단계 이상 전진 속도 (외삽값 약 5.5타일/초)
- 중력 1700 점프
- 연료 소모 모델 (거리 비례인지 시간 비례인지)

- 고정 스텝 주기 (원작 체감에 맞춰 60Hz 또는 70Hz 중 결정)
